## Validation d'archi V1 — le point clé

Écart inattendu qui a demandé un vrai débogage :

- **Moteur validé** : BQ `VECTOR_SEARCH` == FAISS local == cosine exact, **100%** sur vecteurs identiques. Le swap Vertex→BQ ne change rien à la recherche.
- **MAIS** vs le baseline stocké dans `tb_casal_raw_titles` : seulement **75%** de match, avec des écarts **réels** (score médian 0.023, `old_id` souvent rang 3-5), pas du bruit de tie-break.
- Hypothèses éliminées une par une : near-tie (réfuté), task_type (réfuté — voir ci-dessous), base retrieval_doc/V2 (40%, pire), moteur (100%).
- **Conclusion** : les prédictions stockées ne sont **pas un V1 propre** — les embeddings de requête du run de juin diffèrent de tout run reproductible aujourd'hui (dérive modèle ou preprocessing du run de l'époque). Le pipeline actuel est **déterministe** (vecteurs identiques d'un appel à l'autre) → il faut réétablir un V1 propre et rejouable via BQ, et ne plus se fier à l'ancien baseline.

**Découverte utile** : pour `text-embedding-004`, `cos(default, RETRIEVAL_QUERY) = 1.0000` → le `task_type` ne change pas le vecteur de requête. **task_type n'est donc pas un levier** ici (ça enterre définitivement l'axe V2).

## Runs V1 + réflexion validation & reranking (après-midi)

- **V1 catégorisé sur raw + feedgen** (via BQ `VECTOR_SEARCH`, écrit en place dans les tables). Résultats feedgen « un peu bof sur certains » — cause suspectée : on prend le **top-1 direct de l'embedding** (matching lexical, pas de raisonnement).

- **Réflexion validation** (brainstorm parké) : il manque un moyen réfléchi de valider nos méthodes. GMC client écarté (trop souvent faux, c'est ce qu'on corrige). Étalon-or = référentiel **expert humain** (Corentin), mais l'humain ne scale pas. Approche esquissée : petit **jeu gold** (~100-300 produits) validé par *relecture* de prédictions (bien plus rapide que catégoriser à froid) → accuracy top-1/top-k, découpée par score et catégorie, avec **plusieurs catégories acceptables** par produit pour gérer l'ambiguïté. Faiblesse : dépendance à la couverture GPC du jeu → gold à construire *stratifié* + cas ambigus curés, format multi-flux. Idée flux **Loewe abandonnée** (mode = couverture trop étroite, et la table `casal` est déjà un vrai flux client). Sujet à reprendre.

- **Clarification RAG (reranking)** : le reranking porte sur les *résultats récupérés*, pas sur l'index → **décorrélé de Vertex**, parfaitement faisable sur la table BQ (`top_k` large puis rerank). C'est exactement le **V3** prévu.
