## Le bug de fraîcheur du rôle

En me passant administrateur, l'interface a continué d'afficher les écrans éditeur : aucun bouton de validation sur les demandes en attente, et un bouton « Demander la validation » alors que le clic lançait bel et bien la récupération.

Toute la chaîne serveur était juste, vérifiée jusqu'au sous-document Firestore. La cause était côté client : le rôle était lu depuis l'utilisateur que le navigateur garde en `localStorage`, qui n'est rafraîchi qu'au chargement de page. Les routes, elles, voyaient déjà le bon rôle.

Un rechargement suffisait à masquer le symptôme. **Correctif retenu : supprimer la dépendance au cache.** Les réponses des endpoints projet portent maintenant un champ `viewer_role` calculé à la requête, donc les boutons ne peuvent plus être en désaccord avec les autorisations réelles. Le hook `useRole` disparaît.

> Le même piège existe partout où un module lit une autorisation depuis l'objet `user` du navigateur. C'est une classe de bug, pas un cas isolé.

## L'incident « No asset found » : c'est un quota Meta, pas un compte vide

Une récupération lancée sans identifiant de campagne a échoué avec ce message. Les logs de la Cloud Function disent tout autre chose.

**Sans `campaign_id`, le scrapper énumère tout le compte.** Sur le compte `1349117765200572`, cela donne **1545 campagnes**, puis un appel Graph API par campagne pour lister ses ads. Meta a coupé en cours de route :

```
User request limit reached / Ad Account Has Too Many API Calls (code 17)
```

La relance vingt minutes plus tard a échoué dès le premier appel, le compte entier étant désormais throttlé (code 80004). Zéro campagne remontée, donc zéro asset, donc le message final « No asset found », qui ne dit rien du quota.

**Conséquence produit : l'identifiant de campagne n'est pas un filtre de confort, c'est ce qui rend le run réalisable** sur un gros compte. Un projet visant un compte annonceur entier n'est pas exécutable en l'état.

**Bug à signaler aux DS** : `_get_next_pages` fait `response['data']` sans vérifier la présence d'une clé `error`. Dès que Meta répond une erreur au lieu d'une page, la fonction lève un `KeyError` et fait tomber toute la Cloud Function en HTTP 500. Un incident lisible devient un crash muet. Deux lignes de garde suffisent.

## Pourquoi un projet est resté bloqué et pas l'autre

Deux projets ont échoué le même jour, un seul s'est correctement marqué en échec. Comparaison des réponses reçues par le serveur :

| Projet | Réponse HTTP | Durée | État écrit |
| --- | --- | --- | --- |
| TEst 2 | 200, corps `No asset found` | 1 s | `failed`, correctement |
| Lydia | 500, le crash `KeyError` | 606 s | **rien** |

L'historique des jobs BigQuery le confirme : pour Lydia, l'`UPDATE` n'a jamais été tenté.

La cause n'est pas une branche d'erreur manquante, le code gère bien le cas. **C'est que l'observateur qui attend la réponse est une promesse en mémoire**, volontairement détachée pour ne pas faire patienter le navigateur jusqu'à une heure. Il ne peut écrire l'issue que si le process Node est encore vivant à l'arrivée de la réponse. Un run d'une seconde ne risque rien, un run de dix minutes suppose que le serveur survive dix minutes. Ici il ne l'a pas fait : j'éditais les fichiers serveur pendant ce temps, et chaque sauvegarde redémarre le serveur de dev.

C'est exactement la fragilité anticipée hier, cette fois **constatée en conditions réelles**. En production le risque est plus faible mais pas nul, Cloud Run recyclant ses instances. `is_stalled` fait son travail de filet : le projet s'est déclaré bloqué au bout d'une heure et redevient relançable. Le correctif durable reste le même, un identifiant de job côté service ou un passage par Cloud Tasks, pour que l'issue soit écrite par le service plutôt que par un auditeur fragile.

**`project_id` validé** : « yes je pense que c'est une très bonne idée, si jamais y a des scopes différents pour un même client ». C'est l'accord sur la demande numéro un, celle qui lève la contrainte un projet égale un compte annonceur. **Durée d'une Cloud Function au-delà d'une heure** : réponse de Hajar, « techniquement c'est possible mais y a moyen de créer un timeout ». À nuancer avant de s'appuyer dessus. Pour un service Cloud Run déclenché en HTTP, ce que sont ces fonctions, **3600 s est le plafond de la plateforme et non un réglage** : `cf-gather-meta-assets` est déjà déployé exactement à cette valeur. Dépasser l'heure impose de changer de modèle d'exécution, un Cloud Run **Job** allant jusqu'à 24 h par tâche.

Surtout, **allonger le délai ne réglerait pas notre problème**. L'incident du jour l'a montré : la difficulté n'est pas la durée, c'est que l'issue du traitement n'est connue que de celui qui tient la connexion HTTP. Avec 24 h de budget, une connexion perdue perdrait toujours le résultat. La bonne demande côté DS est donc que **la fonction écrive elle-même son statut** : accusé de réception immédiat avec un identifiant de job, puis écriture de l'issue en base à la fin. Cela résout d'un coup les trois défauts connus, le plafond horaire, l'observateur fragile et le HTTP 200 systématique.

## Lot 3 : prise d'avance sur le `project_id`

Commit `23f1c3bcf`, branche `feat/creative-insights-project-id`, poussée. Pas encore de PR.

L'idée : faire toute notre part sans attendre la livraison des DS, de sorte que le travail de Hajar suffise à activer la fonctionnalité.

**La colonne a été créée par nos soins**, `ALTER TABLE meta.tb_api_asset_urls ADD COLUMN project_id STRING`. 1472 lignes, toutes à NULL, aucune donnée touchée, réversible. Le risque a été levé en lisant la **source réellement déployée** de la Cloud Function : le chargement utilise `autodetect=False` avec un schéma explicite et la disposition par défaut `WRITE_APPEND`, donc une colonne ajoutée n'est pas écrasée par les runs suivants.

**Les cinq requêtes du module utilisent un périmètre à repli**, factorisé dans un `scopeClause` unique :

```sql
(project_id = @project_id OR (project_id IS NULL AND ad_account_id = @account_id))
```

Vérifié deux fois, et c'est ce qui compte ici. Sur la vraie table, **1456 créas avant, 1456 après** : le comportement actuel est strictement préservé. Sur un jeu synthétique à deux projets sur un même compte, le projet A voit sa créa et l'ancienne ligne non attribuée de son compte, mais **pas celle du projet B**. C'est le comportement cible.

Le `project_id` part déjà dans le payload : la fonction ne lit que trois clés et ignore le reste.

### Le chiffre qui justifie tout le chantier

Historique de collecte du compte `1349117765200572` :

| Jour | Campagnes | Créas |
| --- | --- | --- |
| 2026-05-12 | 7 | 63 |
| 2026-05-28 | 36 | 142 |
| 2026-05-29 | 7 | 94 |
| 2026-06-01 | 6 | 1122 |
| 2026-08-12 | 1 | 35 |

Un projet dont la collecte propre a ramené **35 créas en affiche 1456**, parce que le périmètre est le compte annonceur et non le projet. Les 1421 autres viennent des essais du prototype des DS de mai et juin. Ce sont exactement les lignes à rattacher pendant la fenêtre de backfill.

### Le `DELETE` de la Cloud Function est déjà buggé

Lecture de la source : `DELETE FROM ... WHERE asset_id IN UNNEST(...)`, **sans aucun filtre sur `ad_account_id`**. Ce n'est donc pas un risque futur lié au `project_id`, c'est un défaut actif : une créa utilisée sur deux comptes voit sa ligne supprimée par un run sur l'autre compte. Argument utile, la correction se justifie indépendamment de notre demande.

### GCS : rien à changer

Question tranchée. Un découpage par projet dupliquerait des fichiers identiques, un `asset_id` désignant une créa Meta et non un projet. Surtout, chaque projet devrait **retélécharger** ses créas depuis Meta, donc multiplier les appels à l'API dont on vient de constater qu'elle nous coupe. La relation projet vers fichier appartient à BigQuery, où `project_id` et `gcs_file_name` sont déjà côte à côte. Vérifié au passage : supprimer un projet n'efface que la ligne BigQuery, jamais les fichiers, donc aucun orphelin à gérer.

Une erreur ESLint dans le module, un import inutilisé de `listAssetFacets`. Et une dérive de formatage dont je suis l'auteur : Prettier avait été lancé avec la configuration du **client** sur des fichiers **serveur**, dont les règles diffèrent, laissant dix fichiers non conformes. Reformatés avec la bonne configuration.
