## Le bug de fraîcheur du rôle

En me passant administrateur, l'interface a continué d'afficher les écrans éditeur : aucun bouton de validation sur les demandes en attente, et un bouton « Demander la validation » alors que le clic lançait bel et bien la récupération.

Toute la chaîne serveur était juste, vérifiée jusqu'au sous-document Firestore. La cause était côté client : le rôle était lu depuis l'utilisateur que le navigateur garde en `localStorage`, qui n'est rafraîchi qu'au chargement de page. Les routes, elles, voyaient déjà le bon rôle.

Un rechargement suffisait à masquer le symptôme. **Correctif retenu : supprimer la dépendance au cache.** Les réponses des endpoints projet portent maintenant un champ `viewer_role` calculé à la requête, donc les boutons ne peuvent plus être en désaccord avec les autorisations réelles. Le hook `useRole` disparaît.

> Le même piège existe partout où un module lit une autorisation depuis l'objet `user` du navigateur. C'est une classe de bug, pas un cas isolé.

## L'incident « No asset found » : c'est un quota Meta, pas un compte vide

Une récupération lancée sans identifiant de campagne a échoué avec ce message. Les logs de la Cloud Function disent tout autre chose.

**Sans `campaign_id`, le scrapper énumère tout le compte.** Sur le compte `1349117765200572`, cela donne **1545 campagnes**, puis un appel Graph API par campagne pour lister ses ads. Meta a coupé en cours de route :

```
User request limit reached / Ad Account Has Too Many API Calls (code 17)
```

La relance vingt minutes plus tard a échoué dès le premier appel, le compte entier étant désormais throttlé (code 80004). Zéro campagne remontée, donc zéro asset, donc le message final « No asset found », qui ne dit rien du quota.

**Conséquence produit : l'identifiant de campagne n'est pas un filtre de confort, c'est ce qui rend le run réalisable** sur un gros compte. Un projet visant un compte annonceur entier n'est pas exécutable en l'état.

**Bug à signaler aux DS** : `_get_next_pages` fait `response['data']` sans vérifier la présence d'une clé `error`. Dès que Meta répond une erreur au lieu d'une page, la fonction lève un `KeyError` et fait tomber toute la Cloud Function en HTTP 500. Un incident lisible devient un crash muet. Deux lignes de garde suffisent.

## Pourquoi un projet est resté bloqué et pas l'autre

Deux projets ont échoué le même jour, un seul s'est correctement marqué en échec. Comparaison des réponses reçues par le serveur :

| Projet | Réponse HTTP | Durée | État écrit |
| --- | --- | --- | --- |
| TEst 2 | 200, corps `No asset found` | 1 s | `failed`, correctement |
| Lydia | 500, le crash `KeyError` | 606 s | **rien** |

L'historique des jobs BigQuery le confirme : pour Lydia, l'`UPDATE` n'a jamais été tenté.

La cause n'est pas une branche d'erreur manquante, le code gère bien le cas. **C'est que l'observateur qui attend la réponse est une promesse en mémoire**, volontairement détachée pour ne pas faire patienter le navigateur jusqu'à une heure. Il ne peut écrire l'issue que si le process Node est encore vivant à l'arrivée de la réponse. Un run d'une seconde ne risque rien, un run de dix minutes suppose que le serveur survive dix minutes. Ici il ne l'a pas fait : j'éditais les fichiers serveur pendant ce temps, et chaque sauvegarde redémarre le serveur de dev.

C'est exactement la fragilité anticipée hier, cette fois **constatée en conditions réelles**. En production le risque est plus faible mais pas nul, Cloud Run recyclant ses instances. `is_stalled` fait son travail de filet : le projet s'est déclaré bloqué au bout d'une heure et redevient relançable. Le correctif durable reste le même, un identifiant de job côté service ou un passage par Cloud Tasks, pour que l'issue soit écrite par le service plutôt que par un auditeur fragile.
