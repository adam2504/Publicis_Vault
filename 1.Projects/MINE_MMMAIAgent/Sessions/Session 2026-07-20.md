# Session — 20 juillet 2026

Projet : [[MMM AI Agent]]

## Contexte

Reprise après une semaine d'absence. Objectif de la semaine recentré sur l'**amélioration du MMM Agent** (les sujets Basma/audiences restant en réactif — pas moteur). Cible du jour : **durcir contre l'hallucination de tool** (item roadmap P0), puis livrer une **v2** déployée.

## Diagnostic — root cause confirmée contre le code

`schema_agent` (`agent.py`) n'a qu'un seul outil (`get_table_info`) et pour seul job de lire le schéma. Mais on lui injectait le **`BUSINESS_CONTEXT` complet** — qui décrit tout le pipeline SQL (« Main SQL queries: you MUST include `AND client_id`… validated before execution »). Pour un agent schéma-only, cette règle est une **amorce** qui le pousse à tenter un `execute_sql` (hors de son toolset) → ADK renvoie **498** → le stream meurt → `no_answer`. Non-déterministe (hallucination LLM).

## Design — décomposition + scoping (brainstorming → spec → plan)

Retenu : découper le `BUSINESS_CONTEXT` monolithique en **blocs composables** et n'injecter à chaque sous-agent que ce dont son rôle a besoin. Approche **conservatrice** validée pour éviter toute régression : **2 retraits sûrs seulement**, zéro perte ailleurs.

- Blocs : `CTX_INTRO`, `CTX_DISPLAY`, `CTX_DISCOVERY_NOTE`, `CTX_SQL_RULES`, `CTX_FIELDS`, `CTX_METRICS`, `CTX_KPI_SELECTION`.
- Composés : `CTX_FULL` (tous), `CTX_NO_SQL` (tout sauf SQL_RULES), `CTX_NONE` (vide).
- **Retrait 1** : `schema_agent` → `CTX_NONE` (le fix).
- **Retrait 2** : `CTX_SQL_RULES` → **uniquement** `query_writer_agent` (les autres n'écrivent pas de SQL → sûr et protecteur).
- Spec (avec **table d'audit ligne à ligne**) + plan d'implémentation dans `Agent MMM/docs/superpowers/`.

## Implémentation (TDD, branche `feat/scope-business-context`)

- `schema_agent` → `CTX_NONE` + instruction durcie (« exactly one tool: `get_table_info`, never call any other »).
- `discovery` / `validator` / `answer` / `root` → `CTX_NO_SQL` ; `query_writer` → `CTX_FULL` (inchangé).
- **Tests déterministes sur la composition** (le refactor rend le fix testable là où un simple tweak de prompt ne l'était pas) — 6 tests verts.
- 3 commits : décomposition (no-op), scoping+durcissement, README.

## Déploiement v2 (blue/green) — 2 bugs d'infra préexistants corrigés

Le déploiement a échoué 2× avant de réussir — **rien à voir avec le refactor**, deux dettes d'infra du repo :

1. **Deps non pinnées** : `adk deploy` installait `google-adk 2.5.0` (latest), dont le toolset BigQuery, déplacé en `integrations/bigquery`, **hard-importe `google.cloud.dataplex_v1`** (non déclaré) → l'engine **crash au démarrage**. Fix : pin `google-adk==1.26.0`. Piège clé : `adk deploy` lit le `requirements.txt` du **dossier agent** (`MMM_Agent/requirements.txt`), **pas** la racine — c'est là qu'il faut poser le pin. Ajout de `--validate-agent-import` (échec rapide avant création d'engine).
2. **Faux négatif Windows** : adk affiche un `✅` en fin de déploiement, non encodable par la console cp1252 → « Deploy failed » **alors que l'engine était bien créé**. Contourner avec `PYTHONUTF8=1`.

- **v2 = `reasoningEngines/7899832715896160256`**, vérifiée **serving** (query test réel). Dette README corrigée au passage (id périmé `4105…` → live `6073…`) + table de mapping **engine ↔ commit**.

## Réflexion — knowledge par client (piste, à creuser)

Idée : donner à l'agent un **knowledge propre à chaque client**, chargé dynamiquement. Rejoint l'item roadmap P2 « personnalisation par client » ([[Synthèse & Roadmap Testing]]) et s'appuie directement sur le **scoping en blocs `CTX_*`** livré aujourd'hui.

**Deux couches de contexte à distinguer :**
- **Global** (même pour tous) = les blocs `CTX_*` compilés dans l'agent, ce que les DS enrichissent.
- **Par client** (varie selon `client_id`) = **chargé au runtime**.

**Mécanisme pressenti** (calqué sur l'existant) :
1. Une **étape de chargement** juste après `context_setter_agent` (qui pose déjà `client_id` dans le `state`) : un tool `load_client_knowledge(tool_context)` — même pattern que `run_discovery`, Python/déterministe — lit `client_id`, va chercher le knowledge du client, l'écrit dans `state["client_knowledge"]`.
2. **Injection** dans `discovery` / `query_writer` / `answer` via le **templating de state d'ADK** (`{client_knowledge?}` dans l'instruction, substitué à l'exécution) → littéralement **un bloc de plus**, scopé comme les `CTX_*`. *(API ADK exacte à confirmer.)*

**Question ouverte (bloque le choix du store/format) — qu'est-ce que ce knowledge et qui le maintient ?**
- **A** — Contexte business rédigé par des humains (secteur, concurrents, cadrage client, ADN des leviers) → pousse vers **GCS markdown par client** (`knowledge/{client_id}.md`, éditable comme le knowledge Basma).
- **B** — Faits dérivés de la donnée (définitions variables, ce qui est modélisé ou non pour ce client) → pousse vers une **table BQ**.
- **C** — Les deux, fusionnés à la volée.

Non tranché. Complémentaire de l'enrichissement DS (couche globale). Détail archi : [[Architecture technique]].
