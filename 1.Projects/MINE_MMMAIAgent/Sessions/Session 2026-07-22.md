## Durcissement anti-hallucination (suite) — la vraie leçon

L'hallucination `execute_sql` a **migré** : `schema_agent` (corrigé le 20/07) → puis `discovery_agent` → puis **`context_setter_agent`**, qui a **zéro contexte SQL** (instruction minimale, un seul tool). Conclusion révisée : **ce n'est pas (que) du priming SQL — c'est une hallucination non-déterministe du modèle Flash**, qui peut toucher n'importe quel sous-agent. Retirer le priming réduit la fréquence mais **ne peut pas l'éliminer** (whack-a-mole).

- **A+B** (baisse la fréquence) : retirer la **syntaxe SQL résiduelle** des blocs partagés (`SELECT MAX(...)`, `SAFE_DIVIDE`) — la garder dans la seule instruction de `query_writer` — + durcir `discovery_agent` (« exactly one tool: run_discovery »).
- **Filet retry backend (C) — le fix robuste** *(revirement vs 20/07 où on l'avait jugé « plus nécessaire »)* : puisque même un agent à zéro priming hallucine, le retry est le **seul mécanisme uniforme**. Implémenté dans `agent.ts` : **1 retry**, uniquement sur le `no_answer` transitoire (pas les erreurs HTTP/stream, timeout, disconnect), même session, champs **`attempt`/`retried`** dans les logs → mesure en monitoring. Logique pure extraite dans `retry.ts` + tests unitaires (vitest). Test d'intégration du câblage jugé trop coûteux → confiance par relecture + preuve en monitoring prod.
